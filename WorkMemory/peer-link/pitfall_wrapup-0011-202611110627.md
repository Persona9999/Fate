2026-11-11 下午到收工：實地接上之後的讀數、沒修完的那一件、重來會痛的幾點。用法看 Peer_Link；第一版的坑在同主題的 pitfall_first-version-20261111。

實地成立的組合
- 桌機 DESKTOP-BC18H3C：一層 NAT、路由器是 Synology（有 UPnP）、對外 IP 是公網位址 ⇒ 當主機，路由器自動開 47800 埠成功（租期 3600 秒）。
- 筆電 LAPTOP-TQRHCKVL：路由器 Archer C54 外面還有一層（路由器回報的對外 IP 是私有位址、跟 STUN 看到的不同）⇒ 當不了主機，當另一端可以。
- 兩台的 NAT 都是「每台 STUN 伺服器看到同一個位址」那一種 ⇒ 之後做 UDP 打洞，這一組條件成立。Tim 問過打洞方案，本小姐說明了份量與前提，他還沒說要做。
- 兩台只有兩個節點時，誰當主機功能上沒有差別，差別只在主機關了線就斷。

設計上咬過人的（已修，7988f4f）
- 「手上有主機的公告就略過主機在 Discord 上的訊息」是錯的：線沒接上時兩條路都進不來。改成只略過現在連著的節點，補送時跟 Discord 進來的那一份對重。
- 公告不進酒館是對的（有 token），但酒館裡完全沒有痕跡會讓人以為沒收到 ⇒ 收到公告、接上時留一則系統訊息。
- 網路量測做成後台頁自動跑（Tim：「是否可以讓後台操作自動跑指令」）。

沒修完：筆電按「當另一端」時後台視窗直接關掉
- 沒有筆電的崩潰報告（在筆電的 SenateData/runtime/_crash/ 最新那一份）。下面是推測。
- 推測：後台頁在視窗模式每一格畫面都跑 StatusLines；另一端模式多讀一次 peer_state.json。Server 換檔的瞬間讀不到 ⇒ 丟例外 ⇒ 頁面沒有接 ⇒ 視窗死掉。主機模式不讀那一份，所以按「啟動主機」沒事。
- 量到的機制（自我測試裡的壓力格，另一條執行緒不經過鎖、照 Server 的寫法連續換檔）：
  舊的讀法（File.ReadAllText）2,376 次裡 1,577 次讀不到；而且讀的人會擋到寫的人換檔。
  改成共享開檔（FileShare.ReadWrite｜Delete）之後：換檔 958 次、被擋 0 次；但 931 次讀裡仍有 188 次沒讀到公告，沒有丟例外。
  ⇒ 下一步要看那 188 次到底讀到什麼（空檔？半份？File.Exists 回 false？）。ReplaceOrMove 在 Replace 被拒時會退到 Copy 覆寫，那條路不是一次到位的，是第一個嫌疑。
- worktree wt_peer 裡沒提交的改動（patch4～6，腳本在暫存區 peer/）：頁面每秒最多讀一次並接住例外、cloudflared 找不找得到只在重讀時算、
  讀檔重試＋共享開檔、寫檔暫存檔名每次不同＋換檔重試、狀態檔的跨行程鎖（peer_state.lock）、記憶體裡的游標（寫檔失敗時同一顆 Server 不會重複寫）。
  壓力格要求「一次都不能讀不到」，在連續換檔下太嚴還是真的有洞，還沒判定。
- 另一個還沒處理的風險：狀態檔是讀出來、改、整份寫回，Server 與 CLI／後台頁都會改 ⇒ 沒有跨行程鎖時後寫的會蓋掉先寫的。鎖已經寫了，在沒提交的那一批裡。

這個 session 的限制（下次別再撞）
- PowerShell 工具不能用；結束行程（taskkill）被擋；`server stop --all` 被擋（逐顆 `--id` 可以）；推 SCP_Core 被擋（Tim 推）。
- 從 Bash 的 heredoc 餵 python 改 C# 會吃掉一層反斜線，內容複雜時連 shell 的引號都會卡 ⇒ 修補腳本用 Write 寫成檔、內容用 raw 字串，再用 python 跑。
- worktree 的 bin 被一顆測試留下的 senate.exe（pid 22648）鎖住 ⇒ 一律 `dotnet build src/Senate.Cli -o <暫存區>/wt_bin2` 再從那裡跑 selftest。那顆行程與 worktree 都還在。
